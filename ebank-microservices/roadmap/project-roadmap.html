1.1 — Spring Boot Anatomy
Understand what a Spring Boot app truly is before writing any complex code.
▾
Spring Boot 3 Maven Java 21 REST
Why This First
You cannot debug what you don't understand. Most developers use Spring Boot without knowing what auto-configuration actually does. This module forces you to understand the wiring before adding complexity.
What You Learn
How auto-configuration works — Spring scans the classpath and configures beans conditionally. If you add a JPA dependency, Spring auto-configures a DataSource, EntityManagerFactory, and TransactionManager.
The application context lifecycle — beans are created in dependency order, not declaration order. Understanding this prevents 90% of startup errors.
Dependency Injection — constructor injection vs field injection. Constructor injection makes dependencies explicit and testable.
Practice Steps
  • Create a Spring Boot 3 project from scratch with Spring Initializr. Choose: Web, Actuator, Lombok, Validation.
  • Build a BookController with GET, POST, PUT, DELETE. No database yet — use an in-memory HashMap.
  • Add @Valid bean validation on your request DTOs. Return proper error messages using @ExceptionHandler.
  • Enable and explore Spring Actuator: /actuator/health, /actuator/beans, /actuator/mappings. Read every bean that Spring auto-created.
  • Write one unit test per endpoint using MockMvc. Understand what @WebMvcTest vs @SpringBootTest loads.
Checkpoint
✓ You can move on when
You can explain what happens line by line when Spring starts up
You know the difference between @Component, @Service, @Repository, @Controller
Your API returns correct HTTP status codes (200, 201, 400, 404, 422)
You can write a test that doesn't start the full Spring context

1.2 — Persistence & The Database Contract
Connect your service to PostgreSQL. Learn what ACID, indexes, and transactions actually mean in practice.
▾
PostgreSQL Spring Data JPA Flyway ACID Indexes
Why This Now
Every microservice owns its database. Understanding how the DB layer works — at the index and transaction level — is the skill that prevents the production slowdowns you'll otherwise debug in 2 years.
What You Learn
B+Tree indexes — how PostgreSQL finds data without scanning every row. The index maps column values to row pointers on disk using a balanced tree. Adding an index speeds reads but slows writes.
Transactions & isolation levels — READ COMMITTED (default in Postgres) vs REPEATABLE READ. What dirty reads, non-repeatable reads, and phantom reads mean and when they happen.
Flyway migrations — schema changes are code. Every DB change is a versioned migration file, tracked in source control.
Practice Steps
  • Add PostgreSQL + Spring Data JPA to your Book service. Run PostgreSQL in Docker: docker run -e POSTGRES_PASSWORD=pass -p 5432:5432 postgres:16
  • Create your first Flyway migration: V1__create_books_table.sql. Add a second migration V2__add_author_index.sql that adds an index on the author column.
  • Use EXPLAIN ANALYZE in psql on a query without index vs with index. Observe the difference between Seq Scan and Index Scan.
  • Write a test that demonstrates a dirty read scenario: start two transactions, write uncommitted data in one, try to read it from the other. Observe isolation level behavior.
  • Add @Transactional to your service methods. Then intentionally cause a failure mid-transaction and verify the database rolls back.
Checkpoint
✓ You can move on when
You can explain why EXPLAIN ANALYZE shows a Seq Scan vs Index Scan
You understand what @Transactional(readOnly=true) does and why it matters
Flyway runs automatically on startup and you never alter a migration that already ran
You can demonstrate a rollback in a test

1.3 — Docker & 12-Factor Configuration
Package your service correctly. Externalize all configuration. Make it run identically in every environment.
▾
Docker Docker Compose 12-Factor App Environment Variables
Why This Now
Every service in this roadmap runs in Docker. More importantly, Factor 3 (Config) is fundamental: configuration that varies between environments must never be in code. Learn this pattern once, apply it everywhere.
What You Learn
Multi-stage Dockerfile — build stage compiles the JAR, runtime stage copies only the JAR into a minimal JRE image. Result: a lean, secure image.
Environment-based config — Spring Boot reads SPRING_DATASOURCE_URL, SPRING_DATASOURCE_PASSWORD from environment variables. The same Docker image runs in dev, staging, and prod — only the env vars differ.
Health checks in Docker Compose — your app container should only start after PostgreSQL is healthy. depends_on: condition: service_healthy.
Practice Steps
  • Write a multi-stage Dockerfile for your Book service. First stage: maven:3.9-eclipse-temurin-21 to build. Second stage: eclipse-temurin:21-jre-alpine to run. Compare image sizes.
  • Move all DB connection config to environment variables. Your application.yml should contain NO credentials — only variable references like ${DB_URL}.
  • Write a docker-compose.yml that starts your app + PostgreSQL together. Add a healthcheck on the postgres service using pg_isready.
  • Verify your app starts cleanly, migrates the DB, and serves requests via curl localhost:8080/books.
  • Add a docker-compose.override.yml for local dev with different env vars (local DB, debug port). Practice environment parity.
Checkpoint
✓ You can move on when
docker compose up starts the full stack from zero in under 60 seconds
No credentials appear anywhere in your application.yml or Dockerfile
Your image is under 200MB
The app waits for Postgres to be healthy before starting

2.1 — Redis: Caching That Actually Works
Add Redis to your service. Learn what to cache, what NOT to cache, and how to measure the impact.
▾
Redis Spring Cache Cache-Aside TTL Cache Invalidation
Why This Now
Redis is in-memory. A cache hit takes ~0.1ms vs ~5ms for a DB query. But caching done wrong causes stale data bugs that are very hard to debug. Learn the patterns before scaling.
What You Learn
Cache-Aside pattern — your app checks the cache first. On miss, reads from DB and writes to cache. On write, invalidate the cache entry. This is the default pattern.
TTL (Time-to-Live) — every cached value must expire. Without TTL, stale data lives forever. Choose TTL based on how quickly data changes and how much staleness is acceptable.
Cache invalidation — the hardest problem in caching. Use @CacheEvict on write operations. Cache the result of findById but evict it on update/delete.
Practice Steps
  • Add Redis to your Docker Compose. Add Spring Cache + Redis dependencies. Configure RedisCacheManager with a default TTL of 5 minutes.
  • Annotate findById() with @Cacheable("books") and update/delete with @CacheEvict. Test: call findById twice, verify only ONE SQL query runs (check logs).
  • Connect to Redis with redis-cli. Run KEYS *, GET, TTL on your cached entries. Watch them expire.
  • Intentionally break cache invalidation (remove @CacheEvict), update a book, then read it — observe stale data. Understand why this is dangerous.
  • Implement a rate limiter using Redis INCR and EXPIRE: allow max 10 requests per minute per IP. Implement it as a Spring interceptor.
Checkpoint
✓ You can move on when
You can articulate what data is appropriate to cache (vs what is not)
You've observed stale data and fixed it with proper cache eviction
You've used redis-cli to inspect cache state directly
Your rate limiter works and you can explain the INCR + EXPIRE pattern

2.2 — Kafka: Your First Event-Driven Flow
Send your first event. Understand what Kafka actually is before you rely on it in microservices.
▾
Apache Kafka Spring Kafka Topics Consumer Groups Offsets
Why This Now
Kafka is an append-only log, not a queue. Messages are retained for days and can be replayed. Consumer groups allow multiple independent readers. This mental model is different from RabbitMQ or BullMQ.
What You Learn
Topics and Partitions — a topic is sharded into partitions. Each partition is an independent ordered log. Parallelism comes from having more partitions than consumers.
Consumer Groups — all consumers in the same group share the topic's partitions. Each partition goes to exactly one consumer in the group. Add a consumer = more throughput. Add a group = fan-out.
Offsets — Kafka tracks how far each consumer group has read via the __consumer_offsets topic. This is how replay works: reset the offset to reprocess old messages.
Practice Steps
  • Add Kafka to Docker Compose (use confluentinc/cp-kafka with KRaft mode — no ZooKeeper). Add Spring Kafka to your Book service.
  • When a book is created, publish a BookCreatedEvent to a book-events topic. The event is a JSON object: {"bookId": "...", "title": "...", "eventType": "CREATED"}
  • Create a separate consumer that listens to book-events and logs each event. Start two instances of the consumer — observe Kafka rebalance the partitions.
  • Use kafka-console-consumer.sh --from-beginning to replay all events. Understand why this is impossible in RabbitMQ.
  • Simulate a consumer failure: stop the consumer mid-processing. Restart it — verify it resumes from where it stopped (the committed offset).
Checkpoint
✓ You can move on when
You can explain what happens to messages when the consumer is down (they wait)
You've replayed events from the beginning and understand what that means
You can see consumer group lag in Kafka (use kafka-consumer-groups.sh)
You understand why fan-out works with multiple consumer groups

3.1 — Splitting the Monolith: Service Boundaries
Apply domain-driven thinking to split your Book API into real microservices. Learn why boundaries matter.
▾
DDD Bounded Context Spring Cloud Eureka Config Server
Why This Now
Microservices are a solution to an organizational problem as much as a technical one. The goal is independent deployability and data ownership. You'll make your first real architectural decision: where to draw the lines.
What You Build
Evolve your Book Library into three services: Book Service (catalog), User Service (accounts, authentication), Order Service (borrows/reservations). Each gets its own database.
What You Learn
Config Server — one Git repo holds all service configurations. Services fetch their config at startup. Change a property in Git = all services pick it up on next restart. Implements 12-Factor Factor 3.
Eureka Service Discovery — services register themselves. The API Gateway resolves service names to addresses. No hardcoded URLs between services.
Database-per-service — Order Service cannot query the Book Service's database. It can only call the Book Service API. This constraint forces proper service design.
Practice Steps
  • Create a Config Server (Spring Cloud Config). Create a Git repo with book-service.yml, user-service.yml, order-service.yml. Each service fetches its config from the Config Server at startup.
  • Set up Eureka Server. Register all three services. Verify they appear in the Eureka dashboard at localhost:8761.
  • Give each service its own PostgreSQL database (three separate schemas in Docker Compose). The Order Service must never access the books table directly.
  • Add an API Gateway (Spring Cloud Gateway). Route /api/books/** → Book Service, /api/users/** → User Service, /api/orders/** → Order Service.
  • When creating an order, the Order Service must verify the book exists — but only via an HTTP call to Book Service. Implement this sync call with OpenFeign.
Checkpoint
✓ You can move on when
docker compose up starts 3 services + 3 DBs + Config + Eureka + Gateway
Changing a property in Git config repo affects the service (after restart)
The Order Service has zero SQL joins or queries touching the books table
All external traffic flows through the Gateway on port 8080

3.2 — Saga Pattern: Distributed Transactions
Handle the hardest problem in microservices: what happens when step 3 of a 5-step business flow fails?
▾
Saga Pattern Choreography Compensation Eventual Consistency Idempotency
Why This Now
ACID transactions don't cross service boundaries. When Order Service and a future Inventory Service both need to update atomically, you need a new pattern. The Saga is the solution — and understanding it is what separates senior from junior distributed systems engineers.
What You Learn
Choreography-based Saga — no central orchestrator. Services react to events. Order created → inventory reserved → payment processed. If payment fails → compensation events are published → inventory is released → order is cancelled.
Idempotency — Kafka delivers at-least-once. Your event handler must be safe to call twice with the same event. Check if the action was already done before doing it again.
Dead Letter Topic (DLT) — if an event handler fails repeatedly (not a transient error), the event moves to a DLT instead of blocking the consumer. You can replay it manually after fixing the bug.
Practice Steps
  • Add an Inventory Service that tracks copies of each book. When an order is created, Order Service publishes OrderCreatedEvent to Kafka.
  • Inventory Service consumes OrderCreatedEvent: check stock → if available, reserve it and publish InventoryReservedEvent. If not, publish InventoryFailedEvent.
  • Order Service consumes both events: on success → update order to CONFIRMED. On failure → update order to CANCELLED.
  • Add the compensation path: if you add a payment step and it fails, publish PaymentFailedEvent. Inventory Service must listen and release the reserved stock.
  • Make your event handlers idempotent: store processed event IDs in a processed_events table. If the same event ID arrives twice, skip it.
Checkpoint
✓ You can move on when
You can draw the complete event flow on a whiteboard (happy path + compensation)
Sending the same Kafka event twice doesn't double-reserve stock
Failed events appear in the DLT and you can replay them
You can explain why eventual consistency is acceptable here

3.3 — Resilience: Circuit Breaker & Security
Prevent cascading failures. Add JWT authentication. Make your system degrade gracefully.
▾
Resilience4j Circuit Breaker Retry JWT Spring Security
Why This Now
In distributed systems, dependencies will fail. Without a circuit breaker, one slow service can exhaust the thread pool of every service that calls it. This is a cascading failure — the entire system goes down because one service is slow.
What You Learn
Circuit Breaker states — CLOSED (normal), OPEN (fail fast), HALF-OPEN (testing recovery). When failures exceed a threshold, the circuit opens. Calls fail immediately with a fallback. After a wait, the circuit tries again.
Fallback strategy — when a dependency is unavailable, what's the acceptable degraded experience? For a book availability check: return "unknown availability" rather than failing the entire order.
JWT at the Gateway — the User Service issues JWTs on login. The API Gateway validates the JWT on every request. Internal services trust the X-User-Id header the gateway injects. No internal service needs to validate JWTs.
Practice Steps
  • Add Resilience4j to Order Service. Wrap the Feign call to Book Service with @CircuitBreaker. Set threshold: open after 5 failures in 10 seconds.
  • Write a fallback method that returns a default response when Book Service is down. Stop Book Service — verify orders still receive a graceful response, not a 500.
  • Add @Retry with exponential backoff (3 attempts, 1s / 2s / 4s). Combine with circuit breaker: retry first, then open the circuit.
  • Add JWT authentication to User Service: POST /api/users/login returns a signed JWT. Configure Spring Security in the Gateway to validate the JWT and reject unauthenticated requests.
  • Test: try to create an order without a JWT → 401. With a valid JWT → success. With an expired JWT → 401. Observe the X-User-Id header inside Order Service logs.
Checkpoint
✓ You can move on when
Stopping Book Service doesn't crash Order Service (fallback works)
You can see the circuit state change in actuator: /actuator/circuitbreakers
Unauthenticated requests return 401, not 500
You can explain the difference between authentication and authorization

4.1 — Metrics: Know Your System's Health
Expose metrics from every service. Build dashboards. Set up alerts before users notice problems.
▾
Prometheus Grafana Micrometer PromQL Custom Metrics
What You Learn
RED Metrics — Rate (requests/sec), Errors (error rate %), Duration (latency p50/p95/p99). These three numbers tell you if a service is healthy.
PromQL basics — rate(http_requests_total[5m]) gives you requests per second over the last 5 minutes. histogram_quantile(0.99, ...) gives you p99 latency. These are the two most important queries.
Custom business metrics — Spring's Micrometer lets you track business events: Counter.builder("orders.created").register(registry).increment(). Track orders per minute, failed payments, cache hit rate.
Practice Steps
  • Add Prometheus + Grafana to Docker Compose. Configure Prometheus to scrape all four services' /actuator/prometheus endpoints.
  • In Grafana, add Prometheus as a datasource. Build your first dashboard: one panel per service showing requests/sec, error rate, and p99 latency.
  • Add custom metrics to Order Service: a counter for orders created, a counter for saga failures, a gauge for active orders (PENDING state).
  • Generate load: write a shell script that sends 100 POST requests. Watch your dashboards update in real time.
  • Set up a Grafana alert: if error rate on Order Service exceeds 5% for 2 minutes, trigger a notification (email or just log). Experience what alerting feels like before you need it.
Checkpoint
✓ You can move on when
You can answer "how many orders per minute in the last hour?" from Grafana alone

4.2 — Distributed Tracing: Follow a Request Everywhere
Add OpenTelemetry. Watch a single request travel through all 4 services. Debug the Saga end-to-end.
▾
OpenTelemetry OTel Collector Tempo Trace Propagation Spans
Why This Is The Key Module
Distributed tracing is what makes microservices debuggable. Without it, a 2-second slow request is a mystery across 4 services. With it, you see exactly where 1.8 of those seconds were spent.
What You Learn
Trace context propagation — the OTel agent injects a traceparent HTTP header on every outgoing request. The receiving service reads it and creates a child span. Kafka: the trace ID is injected into message headers automatically.
OTel Collector as central hub — services send telemetry to one place (the collector at port 4317). The collector routes: metrics → Prometheus, traces → Tempo, logs → Loki. Swap backends without touching services.
Practice Steps
  • Download the OTel Java Agent JAR. Add it to your Dockerfiles: ENTRYPOINT ["java", "-javaagent:/otel-agent.jar", "-jar", "app.jar"]. Configure the agent to export to the OTel Collector.
  • Add OTel Collector + Tempo to Docker Compose. Configure the collector pipeline: receive OTLP → export to Tempo (traces) and Prometheus (metrics).
  • Add Tempo as a datasource in Grafana. Create an order — then find its trace in Grafana's Trace Explorer. See all 4 services as spans on a timeline.
  • Force a Saga failure (send an order for a book with zero inventory). Find the failure trace. See exactly which span failed and what the error was.
  • Add Loki. Configure Logback in each service to output JSON logs with the traceId injected. In Grafana, click a trace span → see the exact log lines from that service at that moment.
Checkpoint
✓ You can move on when
You can find any specific order's complete trace in Grafana in under 30 seconds
Trace spans cross Kafka message boundaries (trace ID visible in consumer logs)
Clicking a trace span shows the correlated log lines from that service
You can identify the slowest step in the Saga from the trace timeline

5.1 — Kubernetes: From Docker Compose to Real Orchestration
Deploy your microservices to K8s. Learn what Kubernetes gives you that Docker Compose cannot.
▾
Kubernetes Helm Deployments Services ConfigMaps HPA
What You Learn
K8s solves Docker Compose's gaps: automatic rescheduling when a pod crashes, rolling deployments with zero downtime, horizontal auto-scaling based on CPU/memory, self-healing, and declarative desired state.
Deployments + Services — a Deployment declares "I want 3 replicas of this container." A Service gives it a stable DNS name and load balances traffic. Pods come and go; the Service always resolves.
ConfigMaps + Secrets — the K8s implementation of 12-Factor Factor 3. Config lives in ConfigMaps, sensitive values in Secrets (base64 encoded, or use Vault). Injected as env vars at runtime.
Practice Steps
  • Install minikube or kind locally. Write Deployment + Service YAML for each of your 4 microservices.
  • Use ConfigMaps for non-sensitive config and Secrets for database credentials. Verify no credentials appear in pod env output.
  • Enable the HPA (Horizontal Pod Autoscaler) on Order Service: scale up when CPU exceeds 70%. Generate load → watch replicas increase automatically.
  • Perform a rolling update: change your Order Service version. Watch pods restart one by one with zero downtime. Roll back using kubectl rollout undo.
  • Configure liveness and readiness probes pointing to /actuator/health/liveness and /actuator/health/readiness. Kill a pod — watch K8s restart it automatically.
Checkpoint
✓ You can move on when
kubectl get pods shows all services healthy
A rolling deployment completes with zero failed requests (tested with watch curl)
Killing a pod results in it being rescheduled automatically in under 30s
HPA scales from 1 to 3 replicas under load

5.2 — Failure Engineering: Break Things on Purpose
The system that has never been broken in production will be. Learn to break it deliberately and fix it confidently.
▾
Chaos Engineering Outbox Pattern Graceful Shutdown Backpressure SLA
What You Learn
Transactional Outbox Pattern — the gap in the Saga: what if the service saves the order to DB but crashes before publishing the Kafka event? The order is saved but the event is never sent. The fix: write the event to a DB outbox table in the same transaction. A separate relay process reads from the outbox and publishes to Kafka.
Graceful shutdown — when a pod shuts down (rolling deploy, scale-down), K8s sends SIGTERM. Your service should finish in-flight requests, commit in-progress Kafka offsets, and exit cleanly. Without this, rolling deploys cause request errors.
Chaos testing — deliberately kill services, inject network latency, partition the network. Verify your circuit breakers, retries, and fallbacks work under real failure conditions.
Practice Steps
  • Implement the Transactional Outbox for Order Service. Add an outbox_events table. Write the event to the outbox in the same @Transactional as the order save. Add a scheduler that reads unprocessed outbox events and publishes them to Kafka.
  • Test the gap: stop Kafka, create an order. Verify the order is saved but the outbox event is pending. Restart Kafka — verify the event is eventually published.
  • Configure graceful shutdown: server.shutdown=graceful in Spring Boot + spring.lifecycle.timeout-per-shutdown-phase=30s. During a rolling deploy, verify in-flight requests complete rather than getting a 500.
  • Add chaos tests: write a test that randomly kills a service pod and verifies the system recovers within SLA. Use kubectl delete pod in a loop.
  • Simulate a slow Book Service (add Thread.sleep(5000)). Verify the circuit breaker opens and order creation continues with the fallback. Verify metrics show the circuit state change.
Checkpoint
✓ You can move on when
No events are lost when Kafka is briefly unavailable (outbox catches them)
Rolling deploys produce zero 500 errors (tested under load)
You've documented what happens to your system under each failure scenario
You can recover from any single service failure within 60 seconds

5.3 — System Design Thinking: Beyond Your Project
Apply what you know to systems at scale. Design URL shorteners, chat systems, leaderboards. Answer system design questions confidently.
▾
System Design Consistent Hashing CAP Theorem Back-of-envelope Trade-offs
What You Learn
Back-of-envelope estimation — before designing anything, estimate the scale. 1M users × 10 requests/day = ~116 req/sec peak. Each request needs 1KB → 116KB/sec storage write. This determines if a single DB is enough or if you need sharding.
CAP Theorem in practice — you can have Consistency and Availability but not both during a Partition. Redis Cluster chooses AP (available under network partition, may serve stale data). PostgreSQL chooses CP (stops accepting writes if it can't reach quorum).
Consistent Hashing — how Redis Cluster distributes data across nodes with 16,384 hash slots. Why adding a node doesn't require rehashing all keys. Used in any sharded system.
Practice Exercises (Design, Don't Build)
  • Design a URL Shortener. 100M URLs/day write, 1B reads/day. Choose: DB schema, caching strategy, ID generation approach (hash vs counter), redirect flow.
  • Design a Real-Time Leaderboard. 1M concurrent players, score updates every second, top 100 must be queried in <10ms. Answer: Redis Sorted Sets. Explain why.
  • Design a Chat System. 50M users, messages must be delivered in order per conversation, offline users must receive messages when they come back online. What do WebSockets, message queues, and databases each handle?
  • Review the bahyoune project now that you understand all the patterns. Identify: what would you add? What would you change? What's missing for production?
  • Write a 1-page architecture document for your Book Library system: decisions made, trade-offs accepted, what you'd do differently at 10x scale.
Checkpoint
✓ You have achieved mastery when
You can estimate scale requirements before choosing a technology
You can explain every decision in your system with its trade-off
You can design a new system from scratch and justify each component
You can look at the bahyoune project and suggest meaningful improvements
